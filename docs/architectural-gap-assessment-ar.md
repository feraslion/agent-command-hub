# تقييم الجاهزية المعمارية وخريطة الفجوات التشغيلية

**نطاق التقييم:** هذا المستند يطابق التقييم المقدم من المالك مع البنية الموجودة في Agent Command Hub في تاريخ إعداده. وهو يميّز بوضوح بين **بنية واجهة أو سياسة موثقة** وبين **قدرة موصولة ومثبتة بالتشغيل من البداية إلى النهاية**. لا يُعامل وجود شاشة أو سجل أو عقد API باعتباره إثباتاً على تنفيذ شيفرة مستخدم أو استقلالية وكلاء.

> **الخلاصة التنفيذية:** المشروع يملك طبقة إدارة وحوكمة متماسكة لبداية منصة شخصية، لكنه لم يعبر بعد «عتبة التشغيل الوكيلي الحقيقي». الأولوية ليست زيادة الشاشات؛ بل إغلاق سلسلة واحدة قابلة للإثبات: طلب معتمد → Runner محلي → أداة مقيدة → مخرجات وأدلة → تحقق ومراجعة.

## 1. مطابقة التقييم بالحالة العملية

| الطبقة | التقدير | القراءة العملية الدقيقة | مستوى الإثبات الحالي |
|---|---|---|---|
| Mobile UI | جيدة | واجهة عربية RTL تشمل المشاريع والمهام والتحكم وWorkspace وسجل Runtime والموافقات والقوالب. | **مثبتة برمجياً**، مع حاجة اختبار جهاز فعلي للتدفقات الحرجة. |
| API | جيدة | tRPC محمي وطبقة بيانات تفرض ملكية المشروع في المسارات الأساسية. | **مثبت بعقود وفحوص TypeScript**. |
| Database | جيدة جداً | Drizzle/Migrations وجداول للحالة والموافقات وWorkspace وطلبات Runtime وحزم TypeScript وقوالبها. | **مثبت بالمخطط والمهاجرات**؛ يلزم اختبار ترقية واستعادة واقعي دوري. |
| Audit | جيدة | تسجّل Workspace وRuntime وقرارات القوالب والتغييرات الحساسة. | **مثبتة منطقياً**؛ لم تُختبر بعد مراجعة تحقيق تشغيلي كاملة. |
| Approval | جيدة جداً | الطلبات الحساسة تُنشأ قبل التنفيذ، ولا تتحول إلى طابور Runner إلا بعد قرار صريح. | **مثبتة في مسار الطلب**؛ لا تغطي بعد كل أدوات مستقبلية. |
| Workspace model | جيدة كبداية | Workspace افتراضية محفوظة في قاعدة البيانات وليست نظام ملفات مالك حقيقياً. | **حد معتمد وصريح**. |
| Sandbox policy | جيدة | سياسة مسارات، محتوى، حزم TypeScript، وDocker بلا شبكة عند Runner. | **سياسة واختبارات رفض**؛ ليست بديلاً عن إثبات بيئة جهاز حقيقية. |
| Local Runner | حقيقي لكن محدود | عميل محلي، heartbeat، مطالبات طلبات، وإعداد Docker مقيد. | **يحتاج اختبار Docker شامل على جهاز المالك**. |
| Task Engine | حقيقي كآلة حالات | خطط وأوامر وخطوات وحالات مراجعة/اعتماد قابلة للتتبع. | **مثبت منطقياً**؛ لا ينسق عملاً وكيلياً فعلياً بعد. |
| Agent Runtime | غير مكتمل | توجد أدوار وسياسات مخرجات وتكلفة، لكن لا توجد حلقة تنفيذ أدوات مرخصة ومثبتة لكل دور. | **جزئي**. |
| LLM orchestration | غير موصول تشغيلياً | Model Gateway وسياسة اختيار وحجوزات تكلفة موجودة، لكن لا توجد دورة تشغيل موثقة تقود أدوات المشروع حتى دليل تسليم. | **جزئي/غير E2E**. |
| Tool calling | غير موصول | لا توجد بعد قائمة أدوات مصادق عليها مع عقود إدخال/إخراج ونطاق مشروع وسجل استدعاء موحد. | **غير مكتمل**. |
| Real project filesystem | غير موجود داخل التطبيق | التطبيق لا يصل إلى ملفات الجهاز؛ وهذا حاجز أمان مقصود. أي وصول مستقبلي يجب أن يبقى من خلال Runner محلي ومجلد مصرح به. | **غير موجود عمداً في الخادم والجوال**. |
| Real test/build execution | غير مكتمل | مسار طلب محدود وصور Runner موجود، لكن التحقق الشامل على جهاز المالك لم يثبت بعد. | **غير مكتمل**. |
| Autonomous loop | غير موجود | العامل الدوري الحالي غير حساس ومقيد بالتخطيط والنبضات والتسجيل؛ لا ينفذ Git أو Docker أو ملفات جهاز. | **غير موجود عمداً**. |
| E2E | غير كافٍ | توجد اختبارات وحدات وتكامل منطقية، دون سيناريو جهاز فعلي يغطي Runner وDocker والموافقة والمخرجات. | **غير كافٍ**. |
| Production reliability | غير مكتملة | لا توجد بعد قياسات إنتاجية كافية أو Queue موزع أو tracing موزع أو سياسة تشغيل عالية التوفر. | **غير مكتملة**. |

## 2. الحواجز التي يجب عدم تجاوزها

| الحاجز | القرار المعماري | السبب |
|---|---|---|
| Git | Pull Request فقط؛ لا دفع أو دمج خفي. | يحافظ على مراجعة التغيير وقابلية الرجوع. |
| ملفات الجهاز | لا وصول من التطبيق أو الخادم إلى ملفات المالك. | يحصر الامتياز في Runner محلي مقترن ومصرح به. |
| التنفيذ | كل تشغيل شيفرة يمر بطلب وموافقة وRunner حي وصورة مقيدة. | يمنع تحول واجهة الحوكمة إلى منفذ تنفيذ غير مراقب. |
| العامل الدوري | لا Docker أو Git أو ملفات جهاز أو أدوات حساسة. | يمنع ادعاء الاستقلالية قبل بناء مسار امتيازات قابل للتدقيق. |
| النماذج | لا استدعاء نموذج أو أداة خارج السياق المنقح والميزانية والسياسة. | يضبط الكلفة والبيانات ونطاق المهمة. |

## 3. خارطة الأولويات المقترحة

| الأولوية | النتيجة المطلوبة | نطاق التنفيذ | معيار القبول القابل للقياس | الاعتماد |
|---|---|---|---|---|
| P0 | إثبات Runner محلي واحد | ربط جهاز، فحص Docker، وتشغيل مثال TypeScript متعدد الملفات معتمد. | مخرجات exit/stdout/stderr وسجل تدقيق وقرار موافقة واحد في تدفق كامل. | جهاز المالك وDocker. |
| P0 | اختبار E2E محكوم | سيناريو آلي يحقن مشروعاً مصغراً ويغطي طلباً ثم موافقة ثم Runner ثم نتيجة. | نجاح المسار وفشل مقصود لمسار الشبكة أو import خارجي. | P0 Runner. |
| P1 | سجل أدوات مقيدة | عقود Tool Registry: الاسم، الإدخال، الإخراج، مستوى القرار، Runner profile، وtimeout. | لا يمكن لوكيل طلب أداة غير مسجلة أو خارج مشروعه. | P0 Runner. |
| P1 | دورة Agent Runtime محكومة | Planner ينتج خطة منظمة، Coder ينتج اقتراحاً، QA يتحقق، Reviewer يلخص الأدلة؛ بلا كتابة مباشرة. | كل انتقال يملك context package وmodel run وartifact أو سبب منع. | Tool Registry وحزمة السياق. |
| P1 | LLM orchestration موصول | ربط Gateway بالدورة أعلاه مع الحجز والتسوية وسقف المحاولات. | عملية نموذج واحدة مكتملة قابلة لإعادة العرض من السجل دون كشف السياق الحساس. | دورة Agent Runtime. |
| P2 | Filesystem محلي مقتصر | عرض وتحرير/تطبيق تغييرات عبر Runner في مجلد مالك مصرح به فقط، مع diff وموافقتين للتغيير الحساس. | رفض أي مسار خارج الجذر المقترن وإثبات عدم قراءة محتوى غير مصرح به. | P0 Runner وTool Registry. |
| P2 | Test/build حقيقي | أدوات `test` و`build` قائمة سماح في صورة أو Runner profile محدد. | artifact مخرجات منقح، timeout، حد موارد، وإعادة تشغيل آمنة. | Filesystem محلي مقتصر. |
| P3 | حلقة شبه مستقلة | العامل يصعّد حالات فقط بعد تعريف مسارات الأدوات والموافقات. | لا تنفيذ حساس تلقائي؛ كل خطوة قابلة للإيقاف والاستئناف. | P1 وP2. |
| P3 | موثوقية إنتاجية | قياس طابور وأخطاء وlatency ثم قرار Redis/Worker مستقل/Tracing موزع بناءً على البيانات. | لوحة مؤشرات وSLO بسيط وخطة استجابة للفشل. | حمل تشغيلي حقيقي. |

## 4. ترتيب التنفيذ المقترح

يبدأ العمل بــ **Runner حقيقي واحد على جهاز المالك**، لا بعدة وكلاء ولا بعد Queue موزع. عند إثبات هذا المسار، يضاف سجل أدوات صغير يتضمن أداة قراءة مقيدة وأداة اختبار فقط. بعد ذلك تُوصل دورة Planner → Coder → QA → Reviewer بحيث تنتج المقترحات والآثار داخل Workspace، ولا تملك أي منها حق التنفيذ أو الكتابة المباشرة. عند وجود أدلة تشغيل كافية، يمكن تقديم أدوات الملفات والبناء ضمن حدود Runner، ثم تقييم الحاجة الفعلية إلى عامل مستقل أو Redis أو مراقبة موزعة.

> **قرار مؤجل:** لا يُبنى وصول مباشر إلى filesystem من التطبيق أو الخادم، ولا ينشط «Autonomous loop» ينفذ تغييرات أو Git. هذان امتيازان تشغيليان، لا ميزتا واجهة.

## 5. لوحة تعريف الإنجاز للمرحلة التالية

| البند | مكتمل عندما |
|---|---|
| Runner E2E | ينجح تنفيذ مثال TypeScript معتمد على جهاز المالك في Docker بلا شبكة، ويظهر الدليل في التطبيق. |
| Tool Registry | لا توجد أداة قابلة للاستدعاء من الوكيل من دون سياسة ومدخلات ومخرجات وسجل. |
| Agent Runtime | يمكن إعادة بناء خط سير مهمة واحدة من التخطيط حتى تقرير QA من السجلات فقط. |
| Filesystem محلي | لا يستطيع Runner الوصول إلا إلى جذر مقترن صراحة، وكل كتابة حساسة تنتظر الموافقة. |
| موثوقية | توجد بيانات تشغيل حقيقية تبرر أي توسعة إلى Redis أو Worker منفصل أو tracing موزع. |

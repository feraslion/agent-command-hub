# سياسة المراجعة الثانوية لتعديلات Workspace الحساسة

## الغرض

لا تُحفظ المسودة الحساسة مباشرة في ملف Workspace. تُخزَّن كاقتراح غير مطبق، وتُنشأ لها موافقة مستقلة بمستوى `APPROVAL`. لا يطبق النظام المحتوى إلا بعد تسجيل قرار الموافقة والتحقق من أن إصدار الملف لم يتغير منذ تقديم الاقتراح.

## إشارات الحساسية

يطلب النظام مراجعة ثانوية إذا تضمن تغيير في `source/` إحدى الإشارات التالية:

| الفئة | أمثلة الإشارات |
| --- | --- |
| تنفيذ أو عملية | `child_process` أو `exec` أو `spawn` أو `eval` أو `process.env` |
| شبكة أو أسرار | `fetch` أو `axios` أو `token` أو `secret` أو `password` أو `api key` |
| صلاحيات أو حذف | `permission` أو `auth` أو `security` أو `rm -rf` أو `delete` أو `git` |

لا تفسر الإشارة بوصفها تهديداً مؤكداً؛ إنها قاعدة تحفظية تطلب قراراً ثانياً قبل الكتابة. التعديلات خارج هذه الإشارات تستمر في مسار المحرر المعتاد وسجل التدقيق.

## حالات الاقتراح

| الحالة | المعنى |
| --- | --- |
| `pending_secondary` | محفوظ للمراجعة ولم يكتب إلى الملف. |
| `applied` | اعتُمد وكتب إلى Workspace بعد تحقق الإصدار. |
| `rejected` | رُفض ولم يتغير الملف. |
| `conflicted` | اعتُمد الطلب لكن إصدار الملف تغير؛ لا يكتب النظام فوق التغيير الأحدث. |

> تُنفذ المراجعة الثانوية يدوياً من شاشة الموافقات. في التطبيق الشخصي الحالي، لا يفرض النظام هوية مراجع مختلفة عن مالك المشروع؛ عند إضافة أعضاء لاحقاً يمكن تقييد القرار بمراجع مختلف.

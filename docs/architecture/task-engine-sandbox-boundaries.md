# Task Engine وSandbox: الحدود التشغيلية

## دورة التنفيذ المنطقية

عند إنشاء خطة Runtime لأمر محجوز، ينشأ محرك المهام دورة واحدة مرتبطة بالخطة، ويحفظ كل خطوة بالوكيل والمسؤولية ومستوى الموافقة. تعالج الحلقة خطوة واحدة في كل دورة: تُكمل خطوات `AUTO` منطقياً، وتنشئ طلب موافقة دائماً لخطوات `REVIEW` و`APPROVAL`، ثم تستأنف عند الاعتماد أو تحجب الدورة عند الرفض.

| الحالة | المعنى |
| --- | --- |
| `queued` | توجد خطوة معلقة قابلة للمعالجة. |
| `awaiting_review` | القرار يحتاج مراجعة قبل الاستمرار. |
| `awaiting_approval` | الإجراء حساس ويتطلب موافقة صريحة. |
| `completed` | اكتملت الخطة منطقياً فقط. |
| `blocked` | رفضت بوابة الموافقة؛ لا توجد إعادة محاولة تلقائية. |

## شاشة الموافقات وسير القرار

تعرض شاشة **مركز التحكم ← الموافقات** الآن صندوق موافقات دائماً على مستوى المالك. يضم كل طلب اسم المشروع، وسياق خطوة المحرك ورقمها إن وجدت، وحالة الدورة المرتبطة. عند الاعتماد أو الرفض، تحفظ الواجهة القرار عبر API المحمية ثم يستدعي الخادم انتقال محرك المهام مباشرة؛ فيكمل الخطوة منطقياً عند الاعتماد، أو يحجب الدورة عند الرفض. يحتفظ سجل الأحداث بكلا القرارين.

> لا يؤدي اعتماد طلب إلى تشغيل shell أو Git أو نشر. القرار يحرك الحالة المنطقية فقط، وتبقى أدوات التنفيذ الفعلية خلف الحدود الموضحة أدناه.

## ما يتم تنفيذه فعلياً الآن

يتم حفظ Workspace وملفاتها وسجل تدقيقها في قاعدة البيانات، وتتحقق سياسة المسار من النطاقات المسموحة. ينشئ Sandbox المنطقية نتيجة تحقق قابلة للتتبع، وتحوّل بوابات Git والنشر والحذف إلى طلبات موافقة صريحة. لا يؤدي اعتماد أي بوابة حالياً إلى Git أو نشر أو حذف؛ إذ تبقى هذه الأفعال محجوبة عمداً.

## ما لا يتم تنفيذه الآن

لا توجد حاوية نظام تشغيل، ولا Docker، ولا shell، ولا تشغيل لاختبارات شيفرة المستخدم، ولا Git CLI، ولا وصول إلى شبكة خارجية. لذلك لا يجوز تفسير «فحص Sandbox ناجح» على أنه اختبار بناء أو تنفيذ شيفرة حقيقي.

> يتطلب الانتقال إلى Sandbox فعلية بيئة حوسبة مخصصة ومعزولة قبل إتاحة أي شيفرة غير موثوقة، مع حد زمني وذاكرة وشبكة ونظام ملفات مستقل لكل تشغيل.

# تقييم مستند «مركز قيادة المشاريع بالذكاء الاصطناعي»

**إعداد:** Manus AI  
**تاريخ التقييم:** 20 أغسطس 2026  
**القرار:** **يعتمد بوصفه رؤية منتج وخارطة اتجاه، مع تعديلات تنفيذية ملزمة.**

> يطوّر المستند المشروع فعلاً لأنه ينقل الهدف من «واجهة لوكلاء» إلى حلقة هندسية مغلقة: **طلب → تخطيط → تنفيذ مقيد → تحقق → مراجعة → موافقة → تسليم**. لكنه لا يصلح كخطة تنفيذ حرفية؛ فبعض مكوناته موجودة بالفعل، وبعضها أوسع من النطاق الشخصي الآمن، وبعضها يفترض Runtime ونموذجاً موصولين لم يثبتا تشغيلهما الفعلي بعد.

## 1. الحكم التنفيذي

المستند مناسب جداً من حيث الرؤية والحوكمة. فمفهومه عن الوكيل كمستخدم أدوات مقيدة، وعن المهمة كوحدة عمل قابلة للتتبع، وعن المرور الإلزامي بالمراجعة والموافقة، يتوافق مباشرة مع Workspace وTask Engine والموافقات وRunner المحلي الموجودين في المشروع. [1] [2]

لا ينبغي إعادة بناء المشروع كـ Monorepo أو إضافة تسعة وكلاء أو فتح أدوات النظام مباشرة. المسار الصحيح هو **تثبيت ما بُني، ثم وصل طبقات مفقودة صغيرة حوله**. لدى المشروع بالفعل أساس البيانات والواجهات والسياسات؛ لذا فإن إعادة الهيكلة الواسعة الآن ستؤخر أول دورة استخدام حقيقية وتزيد مخاطر تكرار مصدر الحقيقة.

| البعد | تقدير الملاءمة | القرار |
| --- | --- | --- |
| الرؤية: مركز قيادة يتابع المشاريع | مرتفع | يعتمد كتعريف منتج رسمي. |
| المهمة والحالات والاعتماد | مرتفع | توجد مقابلات دائمة في API وTask Engine؛ توحيد واجهة المهام هو الأولوية. |
| الوكلاء المتخصصون | متوسط إلى مرتفع | تعتمد الأدوار السبعة الحالية، لا قائمة أدوار جديدة أوسع. |
| أدوات مقيدة وSandbox | مرتفع | يستكمل Runner المحلي وWorkspace؛ لا يمنحهما صلاحيات جديدة الآن. |
| Model Gateway وContext Engine | متوسط | فجوة حقيقية تستحق البناء بعد إثبات Runner وربط الواجهة. |
| Monorepo وخدمات منفصلة | منخفض في الوقت الحالي | يؤجل؛ البنية الحالية Modular Monolith كافية للنطاق الشخصي. |
| تعاون مؤسسات وفوترة وسوق وكلاء | منخفض | يؤجل خارج MVP الشخصي. |

## 2. المطابقة مع واقع المشروع

### ما يطابقه المستند بالفعل

يوجد في المشروع API محمي للمشاريع والمهام والوكلاء وWorkspace والموافقات والتكلفة والأوامر وTask Engine وطلبات Runtime وRunner المحلي. كما أن عمليات Workspace الحساسة تمر بطلب مراجعة، وتُسجل المخرجات وسجل التدقيق. [3] ويوجد Runner محلي مقيد لـ JavaScript وTypeScript المستقلين، مع Docker بلا شبكة وحدود موارد وفحص جاهزية وإعداد محلي مستثنى من Git. [1]

| اقتراح المستند | المقابل الموجود | ما يتبقى |
| --- | --- | --- |
| Command Center ولوحة متابعة | تبويبات المشاريع والوكلاء والمهام والتحكم والمحادثة، مع تكلفة وموافقات وRuntime. | توحيد ملخصات المهام لتقرأ tRPC بدلاً من العينات المحلية. |
| Project وTask وApproval وAudit | مخطط دائم وواجهات `projects` و`tasks` و`approvals` و`events`. | إضافة artifacts ورسائل المهمة وعلاقات الاعتمادات التفصيلية عند الحاجة الفعلية. |
| Planner وCoder وQA وReviewer | قوالب وأدوار متخصصة وماستر برومبت عربي/إنجليزي. | لا توجد دورة استدعاء نموذج حية أو handoff منظم بعد. |
| Tool Runtime محدود | Workspace وسياسات Sandbox وGit/Publish/Delete gates وRunner. | لا توجد قائمة أدوات موحدة مرتبطة بمخرجات نموذج وPolicy Gateway واحد. |
| سجل التنفيذ والتكلفة | أحداث المشروع وخطط Runtime وطلبات التنفيذ وstdout/stderr وتكلفة وتنبيهات. | traces موحدة ومقاييس نجاح الوكيل وتقييمات منظمة. |
| Git وPull Requests | بوابات منطقية، قالب PR، Quality checks، وقواعد `main`. | يجب الحفاظ على فحص الجودة الإلزامي واستعادة المراجعة المستقلة عند توفر مراجع. |

### ما لا ينبغي نسخه حرفياً

لا يوصى الآن ببناء `apps/mobile` و`apps/web` و`apps/api` و`apps/worker` وحزم منفصلة فقط لأن المستند يقترح Monorepo. المشروع الحالي Expo + Express + tRPC + Drizzle يعمل كوحدة معيارية واحدة، والفصل المبكر سيؤدي إلى نقل للملفات والاختبارات من دون إثبات قيمة وظيفية. يفصل أي مكون لاحقاً فقط عند وجود حد تشغيل واضح، مثل Worker طويل الأمد على خادم منفصل.

كما لا يوصى بإضافة وكلاء استقبال ومتطلبات وتوثيق ونشر وتواصل كعمليات مستقلة منذ البداية. تعتمد المنصة أدواراً ثابتة: **Orchestrator وPlanner وCoder وQA وDebugger وReviewer وRelease**. يمكن تمثيل الاستقبال وتحليل المتطلبات بوصفهما مخرجات مهيكلة للـ Orchestrator وPlanner أولاً، بدلاً من مضاعفة قائمة الوكلاء والسجلات وسياسات الوصول.

## 3. الفجوات التي يكشفها المستند بوضوح

المستند مفيد لأنه يوضح أربع فجوات حقيقية لا يعالجها العرض وحده. لا يعني وجود شاشة أو جدول أو قالب أن دورة الوكيل تعمل. يجب التمييز بين القدرة الموجودة في الكود والدليل التشغيلي على جهاز المالك.

| الأولوية | الفجوة | سبب الأثر | القرار العملي |
| --- | --- | --- |
| P0 | PR #4 مفتوح بحالة `CLEAN` وفحص الجودة ناجح؛ يحتوي توسعة Runner والاختبارات والمهاجرات. | القدرات المحلية ليست بعد جزءاً من `main`. | مراجعة PR #4 ودمجه فقط عند موافقة المالك الصريحة. |
| P0 | لم يثبت اقتران Runner وتشغيل Docker على جهاز المالك. | لا يمكن الادعاء بتنفيذ TypeScript/JS معزول فعلياً. | اختبار JS وTS والرفض والإلغاء على جهاز مرتبط قبل زيادة الأدوات. |
| P1 | شاشة المهام ما زالت تعتمد جزئياً على `lib/agent-hub.tsx`. | قد تعرض بيانات لا تطابق الخادم والموافقات. | تحويلها تدريجياً إلى tRPC مع حالات تحميل/خطأ/فراغ واختبارات عقد. |
| P1 | لا يوجد Model Gateway ولا Context Engine تشغيليان. | الأدوار والقوالب لا تستدعي نموذجاً ولا تنتج مخرجات مهيكلة. | بناء طبقة استدعاء خادم-فقط وschema صارمة بعد P0. |
| P1 | لا توجد دورة مكتملة Planner → Coder → QA → Reviewer. | لا يستطيع النظام إكمال مهمة برمجية بأدلة. | ابدأ بتغيير Workspace صغير، لا بمشروع كامل أو أدوات عامة. |
| P2 | لا توجد E2E أو إثبات Android مادي حديث. | تدفق المستخدم والـ APK لا يزالان غير مثبتين. | أضف E2E لمسار حرج واختبار دخان Android داخلي. |
| P2 | لا توجد مراقبة/استعادة تشغيلية مكتملة. | صعوبة اكتشاف وتعافي فشل Worker أو قاعدة بيانات لاحقاً. | مقاييس وتنبيهات ونسخ واستعادة بعد مسار MVP الحقيقي. |

## 4. الحواجز غير القابلة للتنازل

يعزز المستند قواعد المشروع ولا يبرر تجاوزها. تبقى هذه الحدود سارية في كل مرحلة:

| المجال | القرار الملزم |
| --- | --- |
| التنفيذ | لا Shell أو Docker أو شبكة أو Git أو نشر من الوكيل من دون قدرة مثبتة وموافقة مناسبة. |
| Runner | يبقى مقتصراً على ملف JS/TS مستقل بلا imports أو حزم أو شبكة أو متغيرات بيئة داخل الحاوية. |
| Workspace | ليس مجلد المضيف؛ الكتابة مقيدة بالمسارات والسياسات والمراجعة الثانوية للحساس. |
| الأسرار | لا تحفظ رموز Runner أو مفاتيح API أو متغيرات التشغيل المحلية في Git أو stdout/stderr أو الوثائق. |
| GitHub | قاعدة `main` تفرض Pull Request وحل خيوط المراجعة وQuality checks ومنع الحذف والدفع القسري. شرط الموافقة حالياً `0` كتجاوز مؤقت موثق، ويعاد إلى `1` عند توفر مراجع مستقل. [4] |
| النشر | يبقى APPROVAL صريحاً؛ لا يبني هذا التقييم APK/AAB أو ينشر خدمة أو يغير الأسرار. |

## 5. خارطة اعتماد المستند داخل المشروع

### المرحلة A — تثبيت الأساس الموجود

ابدأ بقرار PR #4 ثم باختبار Runner على جهاز المالك. لا تضف Model Gateway أو Agent جديداً قبل إثبات دورة JS وTS المقيدة: اقتران، موافقة، claim، تنفيذ، stdout/stderr، رفض import أو مسار محظور، ثم revoke. هذه هي أقل حلقة حقيقية تثبت طبقة التنفيذ المقترحة في المستند.

**معيار الخروج:** PR #4 له قرار موثق، وتجربة Runner جهازية موثقة أو حالة `environment_required` صريحة.

### المرحلة B — مصدر حقيقة واحد للواجهة والمهمة

حول شاشة المهام وملخصات لوحة القيادة إلى `tasks.list` و`tasks.create` و`tasks.setStatus` المحمية. أضف عرضاً واضحاً للـ lease والموافقة وRuntime عند توفرها، ولا تعدّل كل الشاشات دفعة واحدة. يحقق ذلك قلب نموذج `WorkTask` المقترح من دون تبديل المخطط كاملاً.

**معيار الخروج:** مهمة منشأة من API تتغير حالتها في الواجهة بعد mutation، ولا تظهر عينة محلية في وضع التشغيل المعتاد.

### المرحلة C — Intake وContext مهيكلان

أضف مخرجات منظمة صغيرة للـ Orchestrator/Planner: `goal` و`constraints` و`clarifyingQuestions` و`acceptanceCriteria` و`riskSummary`. ثم أضف اختيار سياق محدود من وثائق المشروع وملفات Workspace ونتائج الاختبار وقرارات المستخدم. لا ترسل المستودع كاملاً ولا تثق بمخرجات نموذج قبل التحقق من schema.

**معيار الخروج:** طلب واحد يتحول إلى متطلبات وأسئلة وخطة مهام قابلة للتعديل والمراجعة، بلا كتابة أو تنفيذ تلقائي.

### المرحلة D — Model Gateway ودورة وكيل واحدة

ابن طبقة موحدة خادم-فقط تبدأ بمزود واحد أو مزودين، وتحفظ الاستدعاء والتكلفة والزمن والـ schema result. نفذ دورة صغيرة: Planner ينتج خطة، Coder يقترح فرقاً فقط، QA يقيم الدليل، وReviewer يقرر أن العمل يحتاج APPROVAL أو إصلاح. لا يبدأ Release أو النشر تلقائياً.

**معيار الخروج:** تغيير Workspace محدود يملك خطة وفرقاً ونتيجة QA وسجل تكلفة وقرار مراجعة قابل للتدقيق.

### المرحلة E — Worker مستمر واختبارات عملية

اختر بقرار صريح بين Runner شخصي متصل وجهاز Worker مستقل. بعدها فقط أضف طابور فعلي واستئناف ومقاييس queue/lease/failure. نفذ E2E لمسار مشروع → مهمة → موافقة → Workspace → Runtime request، ثم اختبار دخان Android داخلي.

**معيار الخروج:** دليل حديث لتدفق حرج على بيئة معتمدة، ومصفوفة تقول بوضوح ما اختبر وما بقي محجوباً.

## 6. النتيجة والتوصية

المستند **يطوّر المشروع ويصحح اتجاهه**، بشرط اعتباره وثيقة منتج مرجعية لا وصفة لإعادة بناء كاملة. أفضل استخدام له هو اعتماد حلقة العمل المغلقة، نموذج المهمة، حدود الأدوات، والتدرج من وكيل واحد إلى دورة مراجعة، مع تجاهل مؤقت لتفكيك Monorepo والأنظمة متعددة المؤسسات والأسواق والفوترة المتقدمة.

> **التوصية التالية الوحيدة:** اعتماد المرحلة A أولاً: اتخاذ قرار صريح بشأن PR #4، ثم ربط جهاز المالك لتنفيذ اختبار Runner المقيد. بعد هذا الدليل فقط يبدأ ربط واجهة المهام ثم Model Gateway.

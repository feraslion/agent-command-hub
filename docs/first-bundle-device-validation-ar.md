# بروتوكول إثبات Runner واختبار Android الداخلي

**الحالة:** جاهز للتنفيذ على جهاز المالك؛ لم يُجر الاختبار الفعلي بعد.  
**الهدف:** إنتاج دليل واقعي على تشغيل Runner المقيد وتحقق داخلي من تدفقات Android، لا محاكاة نتيجة نجاح.

## 1. اختبار Runner المحلي المقيد

| المرحلة | الإجراء على جهاز المالك | الدليل المطلوب | شرط النجاح |
| --- | --- | --- | --- |
| ربط المجلد | ربط جذر `agent-command-hub` في جهازك المحلي. | إمكانية فتح `runner/device/`. | لا يعمل Runner على مسار غير موثوق. |
| بناء الصورة | شغّل `./runner/device/build-typescript-image.sh`. | اكتمال إنشاء `agenthub-runner-ts:5.7.3`. | لا تُحمّل حزم وقت تنفيذ الطلب. |
| اختبار العزل | شغّل `./runner/device/smoke-test-typescript.sh`. | المخرج `runner-ts-smoke: 42`. | لا شبكة، جذر قراءة فقط، 15 ثانية، 256MB، و0.5 CPU. |
| إصدار الإقران | من **الإعدادات → Runner المحلي المعزول**، أنشئ رمز إقران للجهاز. | `runnerKey` و`token` يظهران مرة واحدة فقط. | لا يوضع الرمز في Git أو أي محادثة أو ملف مشترك. |
| حفظ الإعداد | أنشئ `runner/device/.env.runner` محلياً، ثم نفذ `chmod 600` و`./runner/device/run-local-runner.sh --check-config`. | نجاح فحص Docker والصورتين. | لا يتصل العميل بالخادم عند فشل الفحص. |
| الاتصال | شغّل `./runner/device/run-local-runner.sh`. | تظهر حالة **متصل وجاهز** في الإعدادات وRuntime. | heartbeat حديث وقدرات Docker وJS/TS مرئية. |
| إثبات التنفيذ | أنشئ طلب ملف مستقل مسموح به من Workspace، اعتمده، وراقب Runtime. | الحالة ورمز الخروج والمدة وstdout/stderr. | لا يُنفذ طلب غير معتمد، ولا يقبل مساراً أو استيراداً محظوراً. |
| إثبات الرفض | جرب مساراً غير مسموح أو كوداً يحوي import. | سبب رفض واضح في السجل. | لا يُشغّل الكود في الحاوية. |
| الإلغاء | من الإعدادات، ألغِ Runner بعد الاختبار أو عند فقدان الجهاز. | اختفاء القدرة على التنفيذ بعد الإلغاء. | لا يستطيع رمز سابق الوصول. |

## 2. اختبار Android الداخلي

| المسار | الإجراء | النتيجة المتوقعة |
| --- | --- | --- |
| البدء والسمة | افتح المعاينة على هاتف Android وبدّل سمة النظام ثم أعد فتح التطبيق. | تتبع الواجهة السمة من دون نص مقصوص أو وميض شديد. |
| الدخول والجلسة | سجّل الدخول ثم سجّل الخروج وارجع للشاشة المحمية. | تُمسح الجلسة ولا يظهر محتوى المالك بعد الخروج. |
| لوحة القيادة | افتح الرئيسية ثم أنشئ أو اختر مشروعاً حياً. | تُعرض بيانات API أو حالة فراغ صريحة، لا بطاقات عينات. |
| المهام | افتح تبويب المهام وبدّل المرشحات ثم أرسل مهمة `running` إلى التحقق. | تتغير الحالة إلى `verifying` بعد نجاح API ويتحدث السجل. |
| Runtime والموافقات | افتح التحكم وراجع اتصال Runtime والسجل، ثم افتح أي قرار معلق. | تظهر حالة الاتصال والفلاتر والقرار من البيانات الحية. |
| Runner | افتح الإعدادات قبل وبعد heartbeat. | لا تظهر الجاهزية قبل heartbeat؛ تظهر قدرات Docker وJS/TS بعده فقط. |
| التنبيهات | فعّل أو عطّل تفضيلات التنبيه وجرب انتقال التنبيه إلى القسم المناسب. | يحترم التطبيق التفضيل ولا يتعطل عند غياب إذن الجهاز. |

## 3. ما يلزم من المالك قبل إغلاق البنود

| البند | المطلوب منك |
| --- | --- |
| إثبات Runner | جهاز يملك Docker وNode.js 22+ ومجلد المشروع المربوط، مع تنفيذ الخطوات السابقة محلياً. |
| اختبار Android | هاتف Android فعلي، وفتح المعاينة عبر Expo Go أو نسخة داخلية، ثم إرسال أي ملاحظات أو لقطات للمسارات الفاشلة. |
| حوكمة GitHub | موافقة صريحة قبل تغيير إعدادات حماية `main` المقترحة في `docs/main-governance-audit-ar.md`. |

> لا تُعلّم بنود الاختبار الفعلي مكتملة حتى تصل دلائل التشغيل من جهاز المالك.

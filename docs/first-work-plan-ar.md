# خطة العمل الأولى — Agent Command Hub

**الإصدار:** 1.0  
**المالك:** مالك المشروع  
**التاريخ:** 22 أغسطس 2026  
**نقطة الانطلاق:** [طلب السحب #12](https://github.com/feraslion/agent-command-hub/pull/12) مدمج، وفحوص الجودة في GitHub ناجحة.

## 1. الهدف التنفيذي

تحويل النسخة الحالية من مركز تحكم غني بالحوكمة إلى **مسار استخدام شخصي موثّق** يبدأ بتسجيل الدخول والمحادثة والمرفقات، وينتهي بطلب عمل وكيل قابل للمراجعة. لا تهدف هذه الخطة إلى تمكين تنفيذ مستقل غير مراقب؛ بل إلى إثبات أن كل خطوة تنتج دليلاً، وتحافظ على ملكية المستخدم للبيانات، وتطلب قرار المالك قبل أي أثر خارجي أو حساس.

> **قاعدة القرار:** لا تنفيذ للشيفرة، ولا Docker، ولا Git push أو دمج أو نشر، ولا اتصال بمزوّد خارجي، إلا عبر مسار معتمد وموافقة صريحة قابلة للتدقيق.

## 4. الترتيب التفصيلي للأسبوع الأول

### اليوم 1: تثبيت خط الأساس

ابدأ بمراجعة PR #12 ونتيجة فحوصه، ثم تأكد أن نسخة التطبيق بعد تسجيل الدخول تعرض لوحة القيادة والمشاريع والمهام. إذا ظهرت شاشة «تسجيل الدخول مطلوب» في المعاينة غير المسجلة، فهذه ليست مشكلة تشغيل؛ إنها حالة الحماية المقصودة. سجّل فقط أي خطأ يظهر بعد جلسة مصادقة صالحة.

### اليوم 2: إثبات المحادثة والمرفقات

أرسل رسالة تخطيط قصيرة مع ملف نصي غير حساس، مثل متطلبات ميزة أو قائمة قبول. يجب أن يعرض التطبيق المرفق، يحفظ سجل المحادثة، ويستعيده بعد إعادة الدخول. لا تستخدم ZIP يحتوي `.env` أو رموز وصول؛ الحظر عند اكتشافها هو نجاح لضابط الأمان وليس عطلاً.

### اليوم 3: أول قرار وكيل

من شاشة الوكيل، أنشئ **طلب خطة** لمهمة صغيرة قابلة للقياس، مثل «اقتراح معايير قبول لتحسين شاشة المحادثة». راجع المخرج قبل تحويله إلى أي مهمة أو تغيير. هذه المرحلة تختبر مسار الحوكمة، لا قدرة الوكيل على تنفيذ شيفرة.

### اليوم 4: أول مساهمة GitHub بواسطة Jules

بعد أن يربط المالك Jules بحسابه ويقيّد حقه بهذا المستودع فقط، افتح Issue باستخدام قالب Jules. يجب أن يكون الطلب ضيقاً، مثل إضافة اختبار لوحدة محددة أو تحسين نص رسالة واجهة. تتوقف العملية عند PR؛ لا يُدمج تلقائياً. يمكن إضافة CodeRabbit لاحقاً لمراجعة PRs، بعد مراجعة أذونات التطبيق.

### اليوم 5: قرار Runner وOpenRouter

لا تبدأ Runner حقيقياً أو OpenRouter ما لم تكن هناك حاجة ملموسة. إن توفّر جهاز Docker، نفّذ بروتوكول Runner الموثق وخزّن النتيجة. أما OpenRouter فيبقى معطلاً حتى يقدّم المالك مفتاح API من حسابه؛ البديل الحالي يبقي الدردشة عبر النموذج الخادمي المتاح.

## 5. بوابات المنع والإيقاف

| الإشارة | الإجراء الإلزامي | النتيجة |
|---|---|---|
| كشف سر في ZIP أو رسالة | حجب المرفق أو تنقيح النص، وعدم نسخ القيمة إلى السجل | فتح ملاحظة مراجعة فقط. |
| طلب تشغيل Docker أو بناء APK أو Git push | إنشاء طلب أو دليل تشغيل، لا تنفيذ مباشر | ينتظر موافقة المالك وجهازاً مناسباً. |
| PR من Jules أو Copilot | تشغيل فحوص الجودة ومراجعة الفرق | لا دمج آلي. |
| فشل اختبار استضافة يدوي | عرض نتيجة منقحة وتوقف | لا إعادة محاولة دورية ولا تعديل DNS. |
| غياب مفتاح OpenRouter | إبقاء التكامل معطلاً | لا طلب أو تخمين مفتاح. |

## 6. مقاييس النجاح للأولويات P0 وP1

تُعتبر الدفعة الأولى ناجحة عندما ينجز المالك ثلاثة أدلة: دخول ناجح يعيد بيانات الحساب، ومحادثة واحدة بمرفق نصي آمن محفوظ ومنقح، وPR واحد صغير من Jules أو مساهمة بشرية ملتزمة بتعليمات `AGENTS.md`. لا يُقاس النجاح بعدد الوكلاء أو الأتمتة؛ بل بوضوح الدليل، وسلامة الحدود، وإمكانية مراجعة كل تغيير.

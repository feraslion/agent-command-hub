# تصور المنتج: Agent Command Hub

**الإصدار:** 1.0  
**اللغة الأساسية:** العربية مع دعم قوالب ووكلاء متعددة اللغات  
**النطاق:** مساعد شخصي لإدارة وإنجاز مشاريع البرمجيات بمساعدة النماذج والوكلاء، ضمن رقابة بشرية وسجل قابل للتدقيق.

> **الفكرة المحورية:** لا يكون Agent Command Hub نافذة دردشة تضم عدة نماذج، بل يكون **مدير تنفيذ شخصي للمشاريع**. يلتقط هدفك، يحولّه إلى خطة عمل ومهام، يكلّف الوكلاء، يتابع الأدلة، يطلب قرارك عند الخطر، ويعيد إليك تقريراً دقيقاً عما اكتمل وما توقف وسبب ذلك.

## 1. الوعد للمستخدم

يكتب المالك هدفاً بلغة طبيعية، مثل: «أكمل تطبيق المخزون: راجع ما بقي، أصلح الأخطاء، أضف الاختبارات، ثم جهز طلب سحب». لا يفترض النظام أن الطلب مكتمل أو آمن؛ بل يقرأ سياق المشروع، يحدد النواقص، يطلب التوضيح عند الضرورة، وينشئ خطة مرئية.

بعد الموافقة على الخطة، يواصل النظام المتابعة بالنيابة عن المالك ضمن الحدود المعتمدة. يقسم العمل، يوجه كل مهمة إلى الوكيل المناسب، يقرأ نتائج الاختبارات والفروق، يعيد المهمة إلى Debugger عند الفشل المحدود، ويتوقف عند العمليات الحساسة بدلاً من تنفيذها بصمت. عند عودة المالك، يجد ملخصاً واضحاً: ما تم، ما ينتظر قراراً، ما فشل، وما هي الخطوة التالية الوحيدة المقترحة.

| النتيجة التي يريدها المالك | ما يفعله النظام |
| --- | --- |
| «افهم المشروع وأكمل ما بقي» | يبني خريطة مشروع، يحدد الفجوات، ثم يحولها إلى مراحل ومهام ذات معايير قبول. |
| «أصلح هذا الخطأ» | ينشئ مسار تشخيص، يجمع الدليل، يقترح فرقاً، يشغّل التحقق المسموح، ثم يعرض النتيجة للمراجعة. |
| «تابع العمل أثناء انشغالي» | يبقي المهام ضمن Queue وحالة واضحة، ويستأنف فقط عبر Worker/RUNNER مثبتين؛ ولا يدعي الاستمرار عندما لا تتوفر البيئة. |
| «هل أصبح جاهزاً للنشر؟» | يجمع دليل الجودة والموافقات وخطة الرجوع، ويطلب APPROVAL صريحاً قبل أي نشر أو إصدار. |

## 2. دورة التجربة الأساسية

تُبنى كل رحلة حول حلقة واحدة قابلة للتتبع، لا حول رسائل حرة بين وكلاء:

```text
طلب المالك
  → فهم النطاق والأسئلة الناقصة
  → موجز متطلبات وخطة عمل
  → مهام مستقلة ومعايير قبول
  → تفويض مقيد إلى وكيل
  → فرق أو artifact أو نتيجة اختبار
  → QA ومراجعة
  → موافقة عند الحاجة
  → تسليم وتقرير حالة
```

تجعل هذه الحلقة المالك قادراً على المتابعة في أي وقت. كل مرحلة لها حالة صريحة مثل: `needs_clarification` أو `planned` أو `running` أو `waiting_approval` أو `reviewing` أو `blocked` أو `completed`. لا تعني بطاقة «قيد التنفيذ» أن العمل مستمر فعلياً في الخلفية ما لم يثبت Worker أو Runner متصل ذلك.

## 3. واجهة المنتج كما يراها المالك

### أ. صندوق الطلب والموجز

يبدأ المالك من شاشة طلب بسيطة: يصف الهدف، يحدد المستودع أو المشروع، ويختار مستوى الاستقلالية والميزانية. يستجيب Orchestrator بموجز قصير يتضمن الهدف والقيود والافتراضات والأسئلة ومخاطر البداية. لا يبدأ أي تعديل قبل أن يصبح هذا الموجز واضحاً أو يقبل المالك الافتراضات المعلنة.

### ب. خطة المشروع ولوحة العمل

تتحول الخطة إلى مراحل وFeatures ومهام فرعية وارتباطات. كل مهمة تعرض المالك والوكيل المسؤول والحالة والأولوية والاعتماديات ومعيار الإتمام والميزانية ودليل التحقق. تتيح اللوحة للمالك إيقاف مهمة أو إعادة ترتيبها أو طلب تعديل الخطة؛ ولا تخلط بيانات العرض التجريبية مع حالة API الحية.

### ج. مركز التنفيذ والمتابعة

تجمع بطاقة المهمة مخرجات الوكيل، الملفات المتأثرة، الفرق، أوامر التحقق المسموحة، نتائج الاختبارات، تكلفة النموذج، محاولات إعادة العمل، والمراجعة. يقرأ المالك **الوقائع** لا ادعاءات عامة: رمز الخروج، stdout/stderr المنقح، نتيجة الفحص، والقرار التالي.

### د. مركز الموافقات

تظهر كل عملية عالية الأثر بوصف واضح: الإجراء، النطاق، الأثر، المخاطر، البدائل، وخطة الرجوع. يمكن للمالك الاعتماد أو الرفض أو طلب تعديل أو التأجيل. تشمل العمليات الحساسة التنفيذ الفعلي ودمج Git وتغيير الحماية والنشر وتغيير الأسرار والاتصال الخارجي.

### هـ. تقرير التسليم

عند توقف دورة العمل أو إكمالها، يصدر النظام تقريراً موجزاً: الهدف، الأعمال المنجزة، الدليل، العناصر المتبقية، التكلفة، المخاطر المفتوحة، وقرار التسليم أو الحجب. بذلك تصبح متابعة العمل قابلة للمراجعة حتى بعد انقطاع المحادثة.

## 4. الأدوار السبعة المعتمدة

لا يحتاج المنتج إلى وكلاء شكلية أكثر. تعتمد المنصة الأدوار الحالية، ولكل دور مخرج محدد وصلاحية ضيقة.

| الدور | المسؤولية | المخرج المسموح |
| --- | --- | --- |
| Orchestrator | استقبال الهدف، حفظ السياق، ترتيب الدورة، واكتشاف التوقف. | موجز تشغيل وخطة انتقال بين الأدوار. |
| Planner | تحويل الهدف إلى متطلبات ومراحل ومهام واعتماديات ومعايير قبول. | `WorkPlan` مهيكل وأسئلة توضيحية. |
| Coder | اقتراح تعديل محدود داخل Workspace أو تنفيذ طلب مقيد بعد الموافقة. | فرق، مسودة، أو artifact؛ لا نشر ذاتي. |
| QA | تعريف وتشغيل التحقق المسموح وتفسير النتيجة. | تقرير PASS/FAIL ودليل قابل للتكرار. |
| Debugger | فصل الحقائق عن الفرضيات واقتراح أصغر إصلاح. | تشخيص وخطوة تحقق تالية. |
| Reviewer | تقييم النطاق والمخاطر والجودة والأمن؛ لا يعدل مباشرة في البداية. | قرار مراجعة أو قائمة ملاحظات. |
| Release | تجهيز دليل الإصدار وخطة الرجوع وChecklists. | حزمة قرار نشر تتطلب APPROVAL. |

## 5. مكونات المنتج والكيانات الموحدة

تضيف هذه الرؤية طبقة تنظيم فوق الجداول والسياسات الموجودة، ولا تستبدلها. المهم هو توحيد معنى الكيانات بين الواجهة والخادم والوكلاء.

| الكيان | الغرض | علاقته بالبنية الحالية |
| --- | --- | --- |
| `ProjectBrief` | الهدف والقيود والأسئلة والافتراضات وحدود MVP. | إضافة فوق المشروع والسياق الحاليين. |
| `WorkPlan` | مراحل وميزات ومهام واعتماديات ومعايير قبول. | يوسع Task Engine بدلاً من إنشاء نظام موازٍ. |
| `Task` | أصغر وحدة قابلة للتفويض والتحقق. | موجودة في API؛ تحتاج ربطاً كاملاً بالواجهة. |
| `ContextPackage` | مقتطفات وثائق وملفات وقرارات ونتائج اختبار ذات صلة فقط. | يضاف كطبقة اختيار سياق، لا كنسخ للمستودع كله. |
| `ExecutionAttempt` | محاولة Runner/Agent، مدخلاتها ومخرجاتها ودليلها المنقح. | يتكامل مع Runtime requests والأحداث والسجلات الحالية. |
| `Artifact` | فرق، تقرير اختبار، وثيقة، build report أو مخرج قابل للمراجعة. | يستفيد من Workspace وسجل الفروق بدلاً من ملفات مضيف مباشرة. |
| `Approval` | قرار عالي الأثر مع سبب ونطاق وخطة رجوع. | موجود ومربوط بـ Task Engine؛ يبقى بوابة الحوكمة. |
| `ModelUsage` | كلفة وزمن وقدرات النموذج لكل مهمة. | يبنى فوق سجل التكلفة الحالي عند إضافة Model Gateway. |

## 6. الإضافات المفيدة المعتمدة من المستند السابق

اعتمدت الرؤية العناصر التالية لأنها تزيد الفائدة المباشرة من دون تجاوز حدود المشروع:

| الإضافة | قيمتها | طريقة اعتمادها |
| --- | --- | --- |
| موجز الاستقبال والمتطلبات | يحول الطلب الحر إلى هدف قابل للتنفيذ وأسئلة واضحة. | يضاف أولاً كمخرج مهيكل لـ Orchestrator وPlanner. |
| الاعتماديات وDefinition of Done | يمنع إغلاق المهمة لمجرد إنتاج نص أو كود. | يضاف إلى خطة المهام ومعايير QA تدريجياً. |
| Context Package محدود | يحسن جودة النموذج ويقلل التكلفة وتسريب السياق. | يختار ملفات ووثائق وقرارات مرتبطة فقط. |
| Model Gateway | يمنع ربط النظام بمزود واحد ويسجل التكلفة والقدرات. | يبدأ بمزود واحد أو اثنين وخادم-فقط وSchema صارمة. |
| Artifacts وTimeline | يجعل أثر العمل قابلاً للمراجعة لاحقاً. | يوحد Workspace وRuntime والأحداث ونتائج QA. |
| دورة إصلاح محدودة | تسمح بتحسين تلقائي منظم بدلاً من إعادة محاولات مفتوحة. | تحدد بعدد محاولات وسقف تكلفة وسبب توقف واضح. |
| تقييمات ومؤشرات | تقيس نجاح الوكيل والتحقق لا انطباعات المستخدم فقط. | تؤجل لما بعد أول دورة فعلية مثبتة. |

## 7. ما يؤجل عمداً

لا يعتمد التصور حالياً تعدد المؤسسات أو سوق وكلاء أو فوترة تجارية متقدمة أو تشغيل عشرات الوكلاء بالتوازي أو تفكيك Monorepo أو فتح Shell على المضيف أو نشر تلقائي للإنتاج. هذه كلها تزيد سطح المخاطر ولا تثبت أول حلقة استخدام شخصية ناجحة.

كما لا يسمح Model Gateway بإرسال المستودع كاملاً إلى أي مزود، ولا يلغي Runner المقيد، ولا يجعل Coder قادراً على تنفيذ Git أو Docker أو شبكة أو نشر تلقائياً. أي توسعة في الأدوات تمر بقائمة سماح وPolicy Gateway ومراجعة وقرار مناسب.

## 8. خارطة التحويل من الحالة الحالية إلى المنتج المقصود

### المرحلة 0 — تثبيت الحقيقة التشغيلية

اتخاذ قرار بشأن PR #4، ثم إثبات Runner المحلي المقيد على جهاز المالك عبر JS وTS ورفض سياسة وإلغاء Runner. لا تعد هذه المرحلة مجرد إعداد؛ إنها الدليل الأول على أن التنفيذ لا يزال ضمن حدود المنصة.

### المرحلة 1 — لوحة عمل حية

ربط شاشة المهام وملخصات لوحة القيادة بـ tRPC، ثم إضافة حالات التحميل والخطأ والفراغ. المخرج المطلوب هو مهمة حقيقية تنشأ وتتغير حالتها وتظهر موافقتها في الواجهة من مصدر حقيقة واحد.

### المرحلة 2 — Intake وخطة قابلة للمراجعة

إضافة `ProjectBrief` و`WorkPlan` مهيكلين، مع أسئلة توضيحية ومعايير قبول واعتماديات. في هذه المرحلة لا ينفذ الوكيل تغييرات؛ بل يثبت أن النظام يستطيع فهم المشروع وتحويله إلى عمل منظم.

### المرحلة 3 — Model Gateway ودورة وكيل واحدة

إضافة استدعاء نموذج خادم-فقط ومخرجات JSON مهيكلة وكلفة. تنفذ دورة صغيرة: Planner → Coder (فرق فقط) → QA → Reviewer. التغيير الحساس يبقى مسودة حتى اعتماد المالك.

### المرحلة 4 — متابعة حقيقية واعتمادية

اختيار مسار Worker: Runner شخصي متصل أو Worker مستقل معتمد. بعدها تضاف الاستعادة والمقاييس والتنبيهات وE2E لمسار مشروع → مهمة → موافقة → Workspace → Runtime، ثم اختبار Android داخلي.

## 9. قواعد النجاح

يقاس نجاح Agent Command Hub بقدرته على تسليم قرار أو artifact موثق، وليس بعدد الوكلاء أو طول المحادثة. يصبح المنتج مفيداً عندما يستطيع المالك أن يفتح التطبيق بعد ساعات ويعرف بدقة: ماذا حدث، ما الدليل، ما الذي يحتاج قراراً، وما الذي سيحدث عند الاعتماد.

| المؤشر | الإشارة الأولى للنجاح |
| --- | --- |
| وضوح المشروع | كل مشروع نشط يملك موجزاً وخطة ومهاماً وأولوية واضحة. |
| صدق الحالة | لا تُعرض مهمة كمنفذة إلا بدليل Runner أو Worker أو تحقق مسجل. |
| جودة التفويض | كل تعديل يملك سياقاً محدوداً ومعيار قبول ونتيجة QA. |
| الأمان | كل فعل عالي الأثر مرتبط بموافقة وسجل ولا يوجد سر في السجلات أو Git. |
| قيمة الوقت | يصل المالك إلى تقرير حالة ومهمة تالية واحدة من دون إعادة شرح المشروع. |

## 10. القرار التالي المقترح

> **ابدأ بالمرحلة 0 فقط:** خذ قراراً صريحاً بشأن دمج PR #4، ثم اربط جهازك لتشغيل اختبار Runner المحلي المقيد. بعد هذا الدليل، تكون الخطوة العملية التالية هي ربط شاشة المهام بـ tRPC؛ لا يبدأ Model Gateway أو وكيل جديد قبل ذلك.

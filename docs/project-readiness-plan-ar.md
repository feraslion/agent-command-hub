# تقييم الجاهزية وخطة تطوير Agent Command Hub

**تاريخ التقييم:** 20 أغسطس 2026  
**نطاق التقييم:** تطبيق Expo الجوال، الخادم وواجهات tRPC، قاعدة البيانات، Workspace وTask Engine، Android، وGitHub Actions وحوكمة المستودع.

> **الخلاصة التنفيذية:** المشروع متقدم بوصفه منصة تحكم وإدارة لوكلاء هندسة البرمجيات ذات بنية آمنة وشفافة، وهو صالح لمرحلة **ما قبل الإنتاج التشغيلي**. توجد واجهة عربية متعددة الشاشات، بيانات دائمة، مسارات موافقة، سياسات Workspace وSandbox منطقية، وقوالب وكلاء متعددة اللغات. لكن تشغيل شيفرة المستخدم، تشغيل أدوات فعلية، والعامل المعزول ما زالت محجوبة عن قصد بانتظار بيئة Runtime معتمدة. لذلك لا ينبغي وصفه بعد بأنه نظام تنفيذ برمجي مستقل فعلياً.

## 1. الأدلة التي استند إليها التقييم

| المجال | النتيجة المرصودة | الدلالة |
| --- | --- | --- |
| تطبيق الجوال | ستة تبويبات تشغيلية، مع شاشات إضافية للـ Workspace والسجل والإعدادات والتنبيهات. | تغطية جيدة لواجهة التحكم والمشاريع والوكلاء والمهام. |
| الخادم | وحدات مستقلة لـ Runtime الجاف والعامل الجاف وTask Engine وSandbox وسياسات Workspace وقوالب System Prompt. | فصل مناسب للمسؤوليات قبل الانتقال إلى تنفيذ حقيقي. |
| البيانات | **26 جدولاً** ظاهراً في قاعدة البيانات، مع مخطط Drizzle ومهاجرات حتى `0014`. | أساس بيانات دائم واسع يغطي المشاريع والمهام والموافقات والمراقبة والقوالب. |
| الجودة | فحوص TypeScript وLint والبناء نجحت؛ الاختبارات أظهرت **36 ناجحاً و1 متجاوزاً** ضمن 10 ملفات. | سلامة ثابتة جيدة للمنطق الحالي، وليست دليلاً على تشغيل E2E أو على جهاز فعلي. |
| Android | توجد ملفات Android أصلية و`eas.json` وإعداد APK/AAB وملف keystore تصحيح. | جاهزية هيكلية للبناء، لكن لا يوجد إثبات حديث لبناء إصدار موقّع أو فحص Gradle كامل محلي. |
| GitHub | سير Quality checks يعمل؛ توجد قاعدة `main` تفرض مراجعة Pull Request واحدة وتمنع الحذف والدفع القسري. | تحسن واضح في الحوكمة، مع بقاء شرط نجاح CI غير مفروض ضمن قاعدة الدمج الحالية. |

## 2. ما أصبح جاهزاً فعلياً

### أ. طبقة التحكم والحوكمة

تقدم المنصة سجلات للمشاريع والمهام والأحداث والتكاليف والموافقات. كما أن قرار الاعتماد أو الرفض مرتبط بسير Task Engine، وتوجد مراجعة ثانوية لمسودات Workspace الحساسة وسجل فروقات للإصدارات المعتمدة. هذه عناصر قوية لمنصة شخصية تحتاج إلى قابلية تدقيق قبل التفويض الواسع.

### ب. إدارة الوكلاء والقوالب

تدعم شاشة الوكلاء أدواراً متخصصة تشمل Planner وCoder وQA وDebugger، مع قوالب عربية وإنجليزية وماستر برومبت مطابق للغة المحددة. يعرض التطبيق النص النهائي المركب قبل الحفظ، ويحتفظ بتخصيص المستخدم بوصفه ملحقاً بالقالب الأساسي المقيد. هذه البنية مناسبة لإدارة سياق الوكلاء، لكنها لا تشغل نموذجاً أو أداة تنفيذية نيابةً عن الوكيل بعد.

### ج. بيانات ومسارات أمان منظمة

Workspace افتراضية ومقيدة ومسجلة في قاعدة البيانات، وليس في نظام ملفات المضيف. تمنع السياسات المسارات غير الآمنة، وتفرض مراجعة فرق قبل الحفظ. كما تسجل بوابات Git والنشر والحذف والمخاطر، وهو تصميم صحيح لتقليل الأثر قبل توفير Runtime فعلية.

### د. جودة المستودع والتعاون

يوجد الآن `CHANGELOG.md`، وسير `Quality checks` يشغل فحص الأنواع والاختبارات وLint والبناء. كذلك توجد طلبات سحب مفتوحة وناجحة الفحص لقالب Pull Request، وقوالب Issues، وسير تسمية Issues تلقائياً. تُظهر وثائق GitHub أن تسمية Issues عند فتحها يمكن تنفيذها باستخدام `GITHUB_TOKEN` مع أقل صلاحية لازمة وهي `issues: write`.[1] [2]

## 4. خطة التنفيذ المقترحة

### المرحلة 0 — تثبيت الحوكمة والجودة

**الهدف:** ضمان أن ما هو موجود في GitHub يمكن مراجعته ودمجه بأمان.

| المهمة | المخرج القابل للقياس | معيار الإتمام |
| --- | --- | --- |
| دمج طلب السحب #1 | قالب Pull Request على `main`. | ظهور النموذج تلقائياً عند فتح PR جديد. |
| دمج طلب السحب #2 | قالبا Issue للخطأ والميزة على `main`. | إمكان اختيار النموذجين عند إنشاء Issue. |
| دمج طلب السحب #3 | سير `Label new issues` على `main`. | فتح Issue تجريبي وإضافة `triage` ووسم النوع والمجال والأولوية تلقائياً. |
| تقوية قاعدة `main` | Quality checks شرط دمج إلزامي. | رفض الدمج عند فشل أي خطوة من TypeScript أو الاختبارات أو Lint أو البناء. |
| توحيد طلبات السحب | مراجعة طلبات السحب المتراكمة وإغلاق الفروع غير اللازمة بعد الدمج. | عدم وجود فرع حوكمة متروك بلا قرار. |

### المرحلة 1 — تحويل التشغيل الجاف إلى Runner معزول

**الهدف:** تمكين تنفيذ محدود ومدروس من دون المساس بمبدأ الأمان أولاً.

| المهمة | التصميم المقترح | معيار الإتمام |
| --- | --- | --- |
| عقد Runner | أمر موقّع يحدد المشروع والمسارات والأمر المسموح والحدود والـ approval. | رفض أي أمر بلا هوية أو مسارات أو قدرة مصرح بها. |
| بيئة معزولة | حاوية غير جذرية، مساحة عمل مؤقتة، نظام ملفات محدود، شبكة مغلقة افتراضياً وحدود CPU/ذاكرة/زمن. | تنفيذ اختبار آمن وحفظ سجل ومخرجات ووقت انتهاء. |
| بوابة الأدوات | قوائم سماح منفصلة للاختبار والبناء وGit والنشر، مع موافقة صريحة للعمليات عالية الأثر. | لا يستطيع أي قالب أو أمر تجاوز البوابة. |
| إعادة النتائج | حفظ artifacts وstdout/stderr المختصر وحالة التنفيذ في الجداول الحالية. | تظهر نتيجة حقيقية في Task Engine وواجهة Workspace. |
| الإيقاف الطارئ | إلغاء أمر وعزل Runner وفك حجز lease منتهية. | اختبار إلغاء موثق لا يترك عملية أو قفلاً يتيماً. |

### المرحلة 2 — التنفيذ المدعوم بالوكلاء ضمن سياسة مثبتة

**الهدف:** نقل الأدوار من تخطيط منطقي إلى سلسلة عمل قابلة للتتبع من Planner إلى Coder ثم QA.

| المهمة | المخرج القابل للقياس | معيار الإتمام |
| --- | --- | --- |
| إدخال نموذج مضبوط | موجهات تُستدعى من الخادم فقط وبحدود تكلفة وزمن. | لا يظهر مفتاح أو سر في العميل أو السجلات. |
| مدخلات ومخرجات مهيكلة | Schema لخطط الوكيل، والتعديلات المقترحة، ونتائج QA، وفرضيات Debugger. | رفض المخرجات غير المطابقة قبل لمس Workspace. |
| دورة Patch | Planner يخطط، Coder يقترح فرقاً، QA يتحقق، Reviewer يراجع عند الحاجة. | كل تغيير مرتبط بأمر وخطة ودليل وموافقة. |
| مراقبة التكلفة | حدود لكل مهمة ومشروع ونموذج، مع إيقاف وتصعيد عند تجاوز العتبة. | تنبيه قابل للتدقيق قبل أي تجاوز فعلي. |

| اختبار دخان | تسجيل دخول، التنقل، المشاريع، الموافقات، Workspace، الإشعارات، والسمة. | توثيق نتيجة كل تدفق على جهاز واحد على الأقل. |
| إعداد الإصدار | إدارة مفتاح توقيع إنتاجي خارج المستودع وزيادة versionCode وإنتاج AAB. | لا توجد مفاتيح إنتاجية في Git، ويمر فحص التوقيع. |
| مراقبة الأعطال | تجميع أخطاء العميل وسجل إصدار واضح. | ربط كل عطل بنسخة التطبيق وسياق محدود غير حساس. |

## 5. ترتيب التنفيذ العملي

ابدأ بدمج طلبات السحب الثلاثة الناجحة وإلزام Quality checks قبل الدمج. بعد ذلك لا توسع قدرات تنفيذ الوكلاء مباشرة؛ نفذ Runner معزولاً ومقيداً أولاً، لأن المنصة الحالية مصممة عمداً لمنع shell والشبكة وDocker وتنفيذ شيفرة المستخدم. عند توفر هذه البيئة، ابدأ بحالة استعمال صغيرة ومقيدة مثل تشغيل اختبار محدد في مشروع تجريبي، ثم وسع قائمة القدرات بعد توثيق النتائج والمخاطر.

بالتوازي، نفذ بناء Android تجريبياً على جهاز فعلي وأضف اختبار E2E واحداً لمسار مشروع → مهمة → موافقة → Workspace. هذا يثبت السلسلة الأهم للمستخدم ويمنع انتقال المشروع إلى إنتاج شكلي يعتمد فقط على اختبارات وحدات.

## 6. مؤشرات نجاح مقترحة

| المؤشر | الهدف الأول | سبب القياس |

| تغطية التدفقات الحرجة | 3 تدفقات E2E موثقة على الأقل. | إثبات تكامل العميل والخادم والبيانات. |
| زمن استجابة المهمة | زمن انتظار وتنفيذ مرصود لكل أمر. | قياس فاعلية العامل قبل التوسع. |
| نجاح Runner المعزول | 100% من الاختبارات التجريبية ضمن القيود المصرح بها. | إثبات عدم تجاوز حدود الأمان. |
| جودة الموافقات | كل إجراء عالي الأثر مرتبط بقرار ودليل وسجل. | الحفاظ على قابلية التدقيق. |

## 7. قرارات مطلوبة من مالك المشروع

1. اعتماد دمج طلبات السحب المفتوحة #1 و#2 و#3 بعد مراجعتها.
2. تحديد أول حالة استعمال مسموح بها للـ Runner المعزول: اختبار، بناء، تحليل ساكن، أو غير ذلك.
3. اعتماد الحد الأولي للموارد: زمن المهمة، الذاكرة، الشبكة، وقائمة الأوامر المسموحة.
4. تحديد قناة تنبيه تشغيلية لوقوع فشل عامل أو تجاوز تكلفة أو توقف قاعدة البيانات.

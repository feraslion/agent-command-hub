# خارطة الإضافات المقترحة لـ Agent Command Hub

**إعداد:** Manus AI  
**الحالة:** مقترح للمراجعة والاعتماد  
**النطاق:** استخدام شخصي لإدارة وإنجاز مشاريع برمجية بمساعدة الوكلاء، مع تشغيل مقيد وحوكمة بشرية.

> لا تمثل هذه الوثيقة قائمة رغبات متساوية. الأولوية تُمنح لما يثبت أن النظام صادق في حالته، آمن في قراراته، ومفيد في دورة مشروع حقيقية. لذلك لا يُنصح ببدء أي تكامل نماذج أو توسعة لقدرات Runner قبل إغلاق بوابات الإثبات التشغيلية الأساسية.[1] [2]

## طريقة قراءة الجدول

| الرمز | المعنى |
| --- | --- |
| **P0** | بوابة إثبات أو أمان؛ تمنع التوسع قبل إغلاقها. |
| **P1** | قيمة مباشرة للاستخدام اليومي بعد اكتمال P0. |
| **P2** | توسعة مهمة بعد ثبوت دورة العمل الأساسية. |
| **P3** | تحسين اعتمادية أو تجربة متقدم، يؤجل حتى وجود استخدام فعلي متكرر. |
| **AUTO / REVIEW / APPROVAL** | مستوى القرار المطلوب لتنفيذ العمل أو تفعيل القدرة، وفق سياسة المشروع. |

## 1. الإضافات المقترحة بالترتيب

| # | الإضافة المقترحة | القيمة العملية | الأولوية | الاعتماديات وبوابة القبول | القرار |
| --- | --- | --- | --- | --- | --- |
| 1 | **اختبار Runner شامل على جهاز المالك** | يثبت الاقتران، صورة Docker المقيدة، تنفيذ JS وTS، الرفض، والإلغاء بدليل حقيقي. | P0 | ربط جهاز ومجلد مشروع، Docker عامل، ثم توثيق stdout/stderr ورمز الخروج داخل Runtime. | APPROVAL |
| 2 | **لوحة جاهزية Runner وإدارة الأجهزة** | تعرض حالة Docker، الإصدار، الصورة المتاحة، آخر نبض، سبب الانقطاع، وزر إلغاء الاقتران. | P0 | نجاح الاختبار الشامل؛ لا تعرض «جاهز» من دون نبض حي. | REVIEW |
| 3 | **توحيد شاشة المهام مع tRPC** | يلغي ازدواج بيانات العرض المحلية ويجعل حالات المهام والأولوية والوكيل مطابقة للخادم. | P0 | عقود API واختبارات تحويل، حالات تحميل وخطأ وفراغ، ووقف العينات في وضع التشغيل. | REVIEW |
| 4 | **توحيد لوحة القيادة مع مصدر الحقيقة** | يجعل ملخص المشروع، التقدم، المهمة التالية، والتكلفة مستندة إلى بيانات حية لا قيم أولية. | P0 | اكتمال بند المهام ومصدر API موثق لكل بطاقة. | REVIEW |
| 5 | **اختبار مصادقة وجلسة غير متجاوز** | يثبت انتهاء الجلسة، الفصل بين المالكين، وإعادة الدخول بصورة قابلة للتكرار. | P0 | استبدال الاختبار المتجاوز باختبار عقد موثوق. | AUTO |
| 6 | **استعادة حماية `main` ومصفوفة حوكمة GitHub** | يثبت أن الدمج يمر بفحص جودة، وأن الاستثناءات والموافقات مسجلة بوضوح. | P0 | مراجعة ruleset والـ CI الفعليين؛ لا تغيير من دون قرار المالك. | APPROVAL |
| 7 | **اختبار Android داخلي على جهاز فعلي** | يثبت الدخول والتنقل والموافقات والتنبيهات والسمة، بدلاً من الاعتماد على الويب أو الاختبارات الوحدة. | P1 | اكتمال أهم المسارات الحية ومفتاح توقيع خارج Git. | APPROVAL |
| 8 | **موجز مشروع منظم `ProjectBrief`** | يحول الطلب الحر إلى هدف، نطاق، قيود، افتراضات، أسئلة، وميزانية قابلة للمراجعة. | P1 | مصدر حقيقة للمشروع والمهام؛ لا يبدأ تنفيذاً تلقائياً. | AUTO |
| 9 | **خطة عمل مهيكلة `WorkPlan`** | تضيف مراحل وميزات ومهام واعتماديات ومعايير قبول بدل تحويل الطلب مباشرة إلى تنفيذ. | P1 | `ProjectBrief` وتوسعة Task Engine، مع واجهة مراجعة الخطة. | REVIEW |
| 10 | **معايير إتمام وتعريف قبول لكل مهمة** | يمنع إغلاق المهمة لمجرد وجود رسالة أو فرق؛ يطلب دليلاً واضحاً من QA أو Runner. | P1 | `WorkPlan` وربط المهمة بالأدلة. | REVIEW |
| 11 | **إدارة اعتماديات المهام والمسار الحرج** | توضح ما يمنع المرحلة التالية، وتدعم إعادة الترتيب والإيقاف من دون فقد السياق. | P1 | مهام حية متصلة بـ API وخطة عمل. | REVIEW |
| 12 | **حزمة سياق محدودة `ContextPackage`** | تختار فقط الملفات والقرارات والاختبارات ذات الصلة، فتقلل التكلفة وتسرب البيانات. | P1 | سياسة اختيار وتنقيح محتوى قبل أي استدعاء نموذج. | REVIEW |
| 13 | **سجل Artifacts موحد** | يجمع الفرق، تقارير الاختبار، مخططات الخطة، مخرجات Runtime، ووثائق القرار تحت المهمة نفسها. | P1 | ربط Workspace وRuntime والأحداث؛ تخزين منقح ومقتطع. | REVIEW |
| 14 | **خط زمني موحد للمشروع والمهمة** | يعطي المالك تسلسلاً واحداً لما خطط ونفذ وفشل واعتمد، مع روابط إلى الأدلة. | P1 | سجل Artifacts والأحداث الحالية. | REVIEW |
| 15 | **تقرير تسليم وإيقاف موحد** | عند الإكمال أو الحجب، يعرض الهدف والدليل والتكلفة والمخاطر والخطوة التالية الوحيدة. | P1 | WorkPlan وArtifacts وQA والموافقات. | REVIEW |
| 16 | **Model Gateway خادم-فقط بمزود محدود** | يوحد استدعاء النماذج، التكلفة، الزمن، القدرات، ومفتاح الاختيار؛ ولا يضع مفاتيح في الجوال. | P1 | ContextPackage، حدود ميزانية، أسرار خادم، وعقود Zod لمخرجات JSON. | REVIEW |
| 17 | **دورة Planner حية بمخرجات JSON** | تجعل Planner ينتج خطة وأسئلة ومعايير قبول قابلة للتسجيل والمراجعة. | P1 | Model Gateway وProjectBrief، مع رفض المخرج غير المطابق للعقد. | AUTO |
| 18 | **Coder للفرق فقط** | يسمح باقتراح تعديل محدود داخل Workspace من دون صلاحية تنفيذ أو Git أو نشر. | P2 | دورة Planner ناجحة، سياسة Workspace، ومراجعة فرق. | REVIEW |
| 19 | **QA مهيكل وتشغيل تحقق مسموح** | يوثق PASS/FAIL ودليل التحقق، ويربطه بمعيار قبول المهمة. | P2 | فرق Coder، قوالب تحقق مقيدة، وRunner مثبت. | REVIEW |
| 20 | **Reviewer وقرار جودة قبل التطبيق** | يفصل المراجعة عن التعديل ويجعل النطاق والمخاطر وملاحظات الجودة مرئية للمالك. | P2 | QA وArtifacts وسجل فرق. | REVIEW |
| 21 | **حلقة Debugger بإعادة محاولة محدودة** | تحول الفشل إلى فرضيات وفحص تالٍ وإصلاح صغير ضمن عدد محاولات وسقف تكلفة. | P2 | QA حي وسياسة retry وحدود تكلفة. | REVIEW |
| 22 | **حجز تكلفة مسبق لكل محاولة نموذج** | يمنع تجاوز الميزانية قبل الطلب، ويعرض الاستهلاك حسب المهمة والوكيل والنموذج. | P2 | Model Gateway وسجل التكلفة الحالي. | REVIEW |
| 23 | **سياسة اختيار النموذج حسب المهمة** | تختار نموذجاً من قائمة صغيرة وفق القدرة والسقف والزمن، لا وفق ادعاء «الأفضل». | P2 | Model Gateway وقياسات استعمال حقيقية. | REVIEW |
| 24 | **بحث نصي ونطاق زمني وفلاتر محفوظة لسجل Runtime** | يكمل فلاتر الحالة والنوع والأهمية الحالية بعزل سريع لملف أو مخرج أو فترة محددة. | P2 | سجل Runtime الحالي وتخزين تفضيلات محلية فقط. | AUTO |
| 25 | **تصدير سجل Runtime وArtifacts بصورة منقحة** | يسهل مشاركة دليل قابل للمراجعة من دون تسريب secrets أو مخرجات كاملة حساسة. | P2 | سياسة تنقيح واحتفاظ وحدود حجم. | REVIEW |
| 26 | **لوحة صحة تشغيلية** | تجمع عمق Queue وleases المنتهية والـ heartbeat والفشل والموافقات والميزانية في مؤشر واحد صادق. | P2 | Runtime حي وبيانات Task Engine متصلة. | REVIEW |
| 27 | **تنبيهات تصعيد وملخص يومي** | تنبه عند فشل حرج أو قرار معلق أو Runner صامت، مع ملخص بدل إغراق الإشعارات. | P2 | لوحة الصحة وتفضيلات التنبيه الحالية. | REVIEW |
| 28 | **سياسة احتفاظ وتنقيح للسجلات** | تحدد ما يحتفظ به النظام، مدة الاحتفاظ، حجم stdout/stderr، وكيفية حذف أو إخفاء البيانات الحساسة. | P2 | جرد البيانات والسجلات الموجودة؛ اختبار حذف آمن. | REVIEW |
| 29 | **نسخ احتياطي واستعادة لاختبار تجريبي** | يثبت أن مشروعاً تجريبياً يمكن استعادته دون الإضرار ببيانات المستخدم. | P2 | سياسة الاحتفاظ وبيئة اختبار منفصلة؛ لا تجرى استعادة إنتاجية بلا موافقة. | APPROVAL |
| 30 | **فحص تبعيات وأسرار في CI** | يضيف حاجزاً مبكراً للتبعيات الضعيفة والأسرار المضافة بالخطأ قبل الدمج. | P2 | قواعد استثناء منقحة وسير CI حالي. | REVIEW |
| 31 | **اختبارات تكامل E2E لمسار الحوكمة** | تثبت مشروع → مهمة → موافقة → Workspace → Runtime بحالات نجاح ورفض، لا اختبارات وحدة فقط. | P2 | Runner مثبت، UI متصل بـ API، بيانات اختبار معزولة. | REVIEW |
| 32 | **ربط Git بمراجعة Pull Request فقط** | يسمح بتجهيز فرع أو PR وقراءة الحالة بعد سياسة صريحة، من دون دمج أو دفع خفي. | P3 | إثبات Runner وPolicy Gateway وموافقة صريحة لكل عملية خارجية. | APPROVAL |
| 33 | **فحص مستودع وربط مجلد مشروع آمن** | يبني خريطة ملفات، لغات، اختبارات، وملفات حساسة قبل التخطيط، مع عرض الملخص لا نسخ المستودع كله. | P3 | Runner محلي مثبت وسياسة مسارات ومحتوى. | APPROVAL |
| 34 | **قدرة تشغيل متعددة الملفات مستقلة** | تدعم اختبار مشروع صغير متعدد الملفات عبر صورة وسياسة منفصلتين؛ لا توسعة خفية للـ Runner الحالي. | P3 | مراجعة أمنية، lockfile، صورة مخصصة، قائمة سماح، واختبار رفض. | APPROVAL |
| 35 | **Worker خلفي مُدار للمهام غير الحساسة** | يتيح متابعة orchestration أو التنبيهات عندما لا يكون جهاز المالك متصلاً، من دون Docker أو أدوات نظام. | P3 | قرار استضافة صريح، مراقبة، secrets، واستعادة. | REVIEW |
| 36 | **Worker معزول مستقل لبناء المشاريع** | خيار لاحق فقط للمهام التي تحتاج Docker أو أدوات نظام أو بقاء مستقلاً عن جهاز المالك. | P3 | حاجة مثبتة، بيئة Linux ثابتة، إدارة صور وأسرار ومراقبة. | APPROVAL |
| 37 | **طوابير خارجية أو Redis** | تحسن throughput والجدولة متعددة العمال عند ظهور ضغط فعلي، ولا تعد حاجة للنسخة الشخصية الآن. | P3 | قياسات ازدحام حقيقية تثبت أن leases قاعدة البيانات لم تعد كافية. | REVIEW |
| 38 | **مراقبة موزعة مثل OpenTelemetry** | تعطي تتبعاً أدق للطلبات والعمال عند تعدد العمليات أو وجود حركة تشغيلية حقيقية. | P3 | خدمة Worker أو حمل حقيقي وقرار مراقبة. | REVIEW |
| 39 | **وضع قراءة دون اتصال ومزامنة لاحقة** | يسمح بتصفح آخر حالة ومراجعة الأدلة المخبأة، مع عدم تنفيذ قرارات أو تغييرات من دون اتصال. | P3 | تعريف دقيق لما يخزن محلياً وسياسة تضارب. | REVIEW |
| 40 | **تحسينات وصول وتجربة جوال متقدمة** | تشمل أهداف لمس كافية، تركيز قارئ الشاشة، اختصارات للأفعال الحرجة، وروابط عميقة من التنبيه للقرار. | P3 | مراجعة مسارات الاستخدام الأكثر تكراراً واختبار على جهاز فعلي. | AUTO |

## 2. ترتيب التنفيذ الذي أوصي به

| الترتيب | الحزمة | لماذا الآن؟ | نتيجة القبول المختصرة |
| --- | --- | --- | --- |
| 1 | البنود 1–6 | تثبت الحقيقة التشغيلية، مصدر البيانات، الحوكمة، والهوية قبل إضافة قدرة جديدة. | Runner مثبت، واجهة حية، مصادقة وحماية فرع موثقتان. |
| 2 | البنود 7–15 | تحول التطبيق من لوحة متابعة إلى مدير مشروع شخصي يملك موجزاً وخطة وأدلة وتسليماً. | طلب يتحول إلى خطة ومهام وأدلة قابلة للمراجعة. |
| 3 | البنود 16–23 | تضيف الذكاء الاصطناعي في حدود صغيرة قابلة للتدقيق والتكلفة، لا كدردشة حرة. | دورة Planner ثم فرق وQA ومراجعة لحالة استخدام صغيرة. |
| 4 | البنود 24–31 | تجعل الاستخدام المستمر قابلاً للمراقبة والاستعادة والتدقيق. | سجل عملي، تنبيهات صادقة، E2E ونسخ احتياطي تجريبي. |
| 5 | البنود 32–40 | توسع Git والتنفيذ متعدد الملفات والعمال الدائمين فقط عندما تثبت الحاجة والحدود الأمنية. | قرار معماري موثق وقدرة مستقلة مختبرة لكل توسعة. |

## 3. إضافات أؤجلها عمداً

| الإضافة المؤجلة | سبب التأجيل | الشرط الذي يجعلها منطقية لاحقاً |
| --- | --- | --- |
| تعدد المؤسسات والأدوار التجارية | المشروع شخصي؛ تعدد المستأجرين يضاعف تعقيد الهوية والعزل. | ثبوت استخدام متعدد العملاء أو فريق حقيقي. |
| سوق وكلاء أو أدوار إضافية | الأدوار السبعة الحالية تغطي دورة العمل ولا ينبغي إضافة وكلاء شكلية. | وجود مخرج محدد وصلاحية ضيقة وفجوة مثبتة. |
| نشر تلقائي للإنتاج | يزيد الخطر قبل إثبات Runner وQA وخطة الرجوع. | سلسلة إصدار موثقة وAPPROVAL صريح. |
| Docker أو shell أو شبكة مفتوحة للوكلاء | يتعارض مع نموذج العزل الحالي ولا يثبت حاجة المستخدم. | قدرة مستقلة وسياسة وصورة حاوية واختبارات رفض. |
| Microservices وKubernetes وKafka | توسع تشغيلي مبكر لا يخدم استخداماً شخصياً مثبتاً. | حمل أو فرق تشغيل أو متطلبات توفر تثبت عجز Modular Monolith. |
| Vector DB أو نسخ المستودع كاملاً إلى النموذج | يرفع الكلفة وتسرب السياق قبل وجود سياسة اختيار فعالة. | ContextPackage ناجح ومقاييس جودة تبرر الاسترجاع الدلالي. |

## 4. القرار العملي التالي

> أوصي باعتماد **الحزمة الأولى فقط** الآن: ربط جهاز المالك، تشغيل اختبار Runner الكامل، ثم توحيد شاشة المهام ولوحة القيادة مع API الحقيقي. عند ظهور الأدلة، يصبح `ProjectBrief` و`WorkPlan` الإضافة التالية ذات القيمة الأعلى؛ ولا أوصي ببدء Model Gateway قبل ذلك.

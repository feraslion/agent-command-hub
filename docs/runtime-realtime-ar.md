# التحديث اللحظي لتبويب Runtime

## الهدف

يوفر تبويب Runtime قناة WebSocket خفيفة عند توفر اتصال الخادم، بحيث تُحدَّث سجلات التنفيذ وحالة Runner وصندوق الموافقات دون أن يطلب المستخدم تحديث الصفحة. لا تحمل القناة بيانات التنفيذ أو المخرجات نفسها؛ بل ترسل إشارة إبطال صغيرة، ثم يعيد العميل جلب البيانات المصرح بها عبر واجهات tRPC الحالية.

> **المبدأ:** قاعدة البيانات وواجهات tRPC هما مصدر الحقيقة. قناة WebSocket تنبه الواجهة إلى وجود تغيير، ولا تمنح صلاحية إضافية ولا تستبدل التحقق في الخادم.

| العنصر | السلوك |
|---|---|
| المسار | `/api/runtime-updates` عبر `ws` أو `wss` بحسب عنوان API. |
| المصادقة | تعتمد جلسة cookie على الويب، ويرسل العميل الجوال رمز Bearer ضمن رسالة مصادقة أولى؛ لا يوضع الرمز في URL. |
| نطاق الأحداث | مقيد بـ `ownerId`؛ لا يستقبل المستخدم إلا تحديثات Runner وRuntime والموافقات الخاصة به. |
| الرسالة | `runtime.invalidate` مع سبب `runner` أو `request` أو `approval`، دون stdout/stderr أو محتوى Workspace. |
| الاحتياطي | يبقى الاستعلام الدوري كل 8 ثوانٍ فعالاً عند الانقطاع أو بعد الخمول، مع إعادة اتصال متدرجة حتى 10 ثوانٍ. |

## الحالات التي تبث حدثاً

تطلق طبقة البيانات تحديثاً بعد نبض Runner، وحجز التنفيذ، وتقرير النتيجة، وإنشاء طلب Runtime، وإنشاء موافقة، أو حل قرارها. عند وصول الإشارة، تبطل الواجهة استعلامات `isolatedRuntime.listForOwner` و`localRunners.list` و`approvals.inbox` فقط، ثم تسترد البيانات الحديثة ضمن المصادقة العادية.[1] [2]

## حد الاستمرارية

اختيرت القناة الخفيفة من دون تشغيل خادم دائم. لذلك تظهر عبارة **«تحديث لحظي متصل»** حين تصادق القناة، وتتحول إلى **«تحديث احتياطي كل 8 ثوانٍ»** عند الانقطاع. هذا يضمن مراقبة قابلة للاستخدام في نمط النشر الحالي، لكنه لا يعد باتصال مستمر خلال الخمول أو إعادة تشغيل الخادم. عند الحاجة إلى اتصال دائم، يمكن نقل القناة نفسها إلى عملية مستمرة من دون تغيير العقد أو واجهة التطبيق.

## التحقق

تغطي اختبارات `runtime-realtime.test.ts` تحويل عنوان API إلى WebSocket وتمييز رسائل الإبطال. اجتازت النسخة TypeScript و53 اختباراً وLint والبناء.
